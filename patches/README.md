# Правки к чужому коду

Здесь лежат заплатки к зависимостям, которые нам нужны, но живут не у нас.
Каждая обязана нести причину, способ проверки и указание, когда её выбросить.

## sing-box: владелец локального SOCKS UDP (`_overlay`)

**Зачем.** В sing v0.8.12 `socks.HandleConnectionEx` передаёт для UDP ASSOCIATE
исходный адрес управляющего TCP-соединения. В sing-box v1.13.18 поиск процесса
использует `metadata.Network`, уже равный `udp`, и ищет TCP-порт в UDP-таблице.
Правило по программе может не сработать либо получить владельца постороннего UDP-сокета.

**Что правится.** `_overlay/sing-box/route/process_cache.go` выбирает TCP-поиск
только для UDP, пришедшего через SOCKS/mixed. Для TUN сохраняется поиск реального
UDP-сокета. Конечный UDP-адрес не используется как адрес управляющего TCP-сокета.
Файл применяется штатным `_overlay/prepare.sh`; кэш модулей не меняется.

**Проверка.** `TestUDPTransportThroughProfile/process-direct` передаёт настоящие
UDP-датаграммы через локальный SOCKS и пропускает их только при совпадении имени
текущего процесса. Без правки тест не получает ответов, с ней проходит.
`TestUDPProcessLookupFromTunSource` отдельно проверяет настоящий UDP-порт
с метаданными TUN без создания интерфейса и без подстановки `ProcessInfo`.

**Когда выбросить.** После исправления определения источника наверху: оба теста
должны проходить без этой копии `process_cache.go`. При обновлении sing требуется
снова проверить контракт `HandleConnectionEx`, даже если версия sing-box прежняя.

## sing-box-ruleset-lock.patch

**Зачем.** Открывает возможность менять маршруты, не обрывая живой туннель.

Набор правил `type: "local"` ядро перечитывает по изменению файла и подменяет
правила под замком, не трогая ни туннель, ни остальную конфигурацию. Это
единственный такой способ: `PUT /configs` в Clash API возвращает пустое тело,
`PATCH /configs` меняет только режим, `/rules` отдаётся лишь на чтение.

Но подмена гонится с маршрутизацией. Запись `rule_set_local.go:146` против
чтения `rule_set_local.go:215` — обход среза правил без `RLock`, из потока
маршрутизации, на каждое соединение. Соседние `Metadata` и `ExtractIPSet`
замок берут, то есть это недосмотр, а не решение.

**Против чего.** `github.com/sagernet/sing-box v1.13.18` (закреплено в
`go/cmd/nekobox_core/go.mod`). Проверено, что в `v1.14.0` то же место
по-прежнему без замка: `Match` там зовёт `matchAnyHeadlessRule(s.rules, …)`.
Поднятие версии эту гонку не лечит.

**Как применить.** Заплатка правит чужой модуль, поэтому нужен свой форк
sing-box и `replace` на него в `go/cmd/nekobox_core/go.mod`. Правка в кэше
модулей не годится: он проверяется по контрольным суммам.

```
git clone https://github.com/SagerNet/sing-box && cd sing-box
git checkout v1.13.18
git apply /путь/до/sing-box-ruleset-lock.patch
```

**Как проверить.** `go/cmd/nekobox_core/live_ruleset_test.go` — тот самый
набор, которым гонка и найдена:

```
CGO_ENABLED=1 go test -race -tags "with_clash_api,with_gvisor,with_quic,with_wireguard,with_utls,with_v2ray_api" -run TestLiveRuleSet ./...
```

Без заплатки красный, с заплаткой зелёный. Измерено 4 сентября 2026 на
Windows: та же проверка, тот же вендоренный `v1.13.18`, отличается только
`replace` на исправленную копию.

**Когда выбросить.** Как только исправление приедет наверх. Признак: тот же
набор под `-race` зелёный без всякого `replace`.

## sing-box: клиент REALITY для серверов Xray 26.9.8+ (`_overlay`)

**Зачем.** 8 сентября 2026 в `xtls/reality` вошёл коммит `8cdf7bf9c7f0`:
сервер узнаёт клиента, только если в `key_share` ровно одна доля
X25519MLKEM768 и стоит она перед обычной X25519. С ним вышли Xray 26.9.8 и
26.9.9. Штатный sing-box эту долю, наоборот, вырезает, поэтому ни одна его
версия с такими серверами не соединяется (SagerNet/sing-box#4520, открыт), а
клиент видит только «reality verification failed». У нас это всплыло
13 сентября 2026 на панели orsana после её обновления до 26.9.8.

**Что правится.** ClientHello правится в `common/tls/reality_client.go` из
`github.com/sagernet/sing-box v1.13.18`. Правленая копия лежит в
`go/cmd/nekobox_core/_overlay/sing-box/common/tls/`, в её шапке перечислены все
изменения ClientHello. Дополнительная проверка PQV описана ниже.

**Как применяется.** Форком на время сборки, а не в репозитории.
`_overlay/prepare.sh` копирует модуль sing-box той же версии из кэша в
`_overlay/build/`, кладёт туда правленый файл и пишет рядом с `go.mod` файл
`go.overlay.mod` с `replace` на эту копию; сборка и тесты идут с `-modfile`.
Закоммиченный `go.mod` не меняется, кэш не трогается. Заодно скрипт сверяет
версию sing-box в `go.mod` со строкой `overlay-base` в каждой копии: поднимут sing-box,
не переснимая копию, — и сборка откажет с понятной причиной. `-modfile`
передают `libs/build_go.sh` и шаг «Test Go» в CI.

```
cd go/cmd/nekobox_core
go build -modfile "$(bash _overlay/prepare.sh)" -tags "…" .
```

**Почему не `-overlay`.** Он был первым выбором — подменить ровно один файл для
компилятора, — но Go на файлы из кэша модулей его не пускает: «Files beneath
GOMODCACHE must not be replaced». Проверено 14 сентября 2026 на Go 1.26.1.

**Как проверить.** `go/cmd/nekobox_core/reality_mlkem_test.go` повторяет проверку
нового сервера дословно — отбор долей, общий секрет, расшифровку session ID —
для каждого отпечатка. Без `-modfile` набор красный, с ним зелёный.

**Когда выбросить.** Когда sing-box сам начнёт слать гибридную долю (#4520):
признак — тот же набор зелёный без `-modfile`.

## sing-box: дополнительная проверка REALITY ML-DSA-65 (`_overlay`)

**Зачем.** Подписка может содержать `pqv`: 1952-байтный открытый ключ
ML-DSA-65. Штатный sing-box v1.13.18 такого поля не понимает. Переключение на
внешний Xray добавляет отдельный процесс со своим выбором маршрута; нативный
клиент теперь понимает `tls.reality.mldsa65_verify` и сохраняет fingerprint.
Ссылка с PQV должна передавать ключ в это поле; удалять ключ при построении
конфигурации нельзя.

**Протокол.** Повторяется проверка из
[Xray v26.9.9](https://github.com/XTLS/Xray-core/blob/v26.9.9/transport/internet/reality/reality.go)
и серверная подпись из
[XTLS/REALITY 8cdf7bf9c7f0](https://github.com/XTLS/REALITY/blob/8cdf7bf9c7f0/handshake_server_tls13.go).
Сначала проверяется HMAC-SHA512 открытого ключа Ed25519. Затем тем же HMAC
считается сообщение с добавленными исходными байтами ClientHello и ServerHello;
ML-DSA-65 с пустым контекстом проверяет подпись из расширения сертификата OID
`0.0`. Отсутствующая, повреждённая или повторная подпись вызывает отказ при
заданном PQV. Обычная REALITY без PQV сохраняет прежнюю проверку HMAC.
Верификатор читает сертификаты из `VerifyPeerCertificate`, без unsafe-доступа
к внутренним полям uTLS. Ключ проверяется при создании конфигурации и
сохраняется при Clone.

**Как применяется.** `prepare.sh` копирует также `option/tls.go` и помощник
`common/tls/reality_mldsa65.go`. Зависимость CIRCL v1.6.4 закреплена в модуле
ядра; она предоставляет стандартную ML-DSA-65 и не требует изменения остальных
закреплённых зависимостей.

**Как проверить.** CI отдельно запускает тесты исправленного TLS-пакета:

```bash
cd go/cmd/nekobox_core
MODFILE=$(bash _overlay/prepare.sh)
go test -modfile "$MODFILE" -tags with_utls github.com/sagernet/sing-box/common/tls -run TestRealityMLDSA65
```

Тесты подписывают настоящий DER-сертификат по протоколу Xray, проверяют
корректную подпись и отказ при другом ключе, повреждении HMAC, подписи,
ClientHello или ServerHello, отсутствующей подписи/транскрипте, неправильном
OID и повторном расширении. Отдельно проверяются формат/размер ключа и Clone.

На Windows 14 октября 2026 изолированное ядро без TUN прошло HTTPS с проверкой
сертификата назначения: Cloudflare 200 и Google 204 с Firefox/Chrome, с PQV и
без него. Однобайтная подмена PQV дала отказ ML-DSA-65. Тест использовал
`route.auto_detect_interface: true`, чтобы действующий пользовательский TUN
не перехватывал соединение второго ядра. Внешний Xray 26.9.9 также прошёл оба
fingerprint и PQV с `streamSettings.sockopt.interface` на обычный интерфейс;
его отказ без этой привязки не доказывает несовместимость Firefox. Проверка
его ClientHello на loopback подтвердила гибридную долю перед обычной X25519.
Ключи, адрес сервера и журналы таких проверок в репозиторий не включаются.

**Когда выбросить.** Когда sing-box поддержит это поле и те же проверки
ML-DSA-65 и ClientHello пройдут без копий из `_overlay`. Удаление только
ClientHello-правки не заменяет поддержку PQV.

## sing-box: маршрут Windows к внутренним адресам (`_overlay`)

**Зачем.** При включённом `auto_detect_interface` штатный прямой выход
привязывается к обычной сетевой карте. Частный адрес рабочего VPN тогда
недоступен через прокси, хотя Windows без прокси уже выбирает нужный TAP-адаптер.
Это касается и HTTPS, и запросов к внутреннему DNS-серверу.

**Что правится.** `route/network.go` из закреплённого sing-box v1.13.18
получает один вызов перед возвратом интерфейса по умолчанию. Для частных,
loopback и link-local адресов Windows выбирает интерфейс через
`GetBestInterfaceEx`; затем проверяются состояние адаптера и его имя/описание.
`neko-tun` и `sing-tun` исключаются, чтобы не возвращать пакет в свой TUN.
Публичные адреса сохраняют прежнюю привязку. Явный `bind_interface` выше этой
автоматики, а выбор выхода по пользовательским правилам не меняется.

Вызов выполняется для каждого нового TCP/UDP-сокета: индекс VPN-адаптера
не сохраняется между переподключениями. На остальных ОС дополнительный
вызов возвращает «нет результата», сохраняя прежний выбор интерфейса.
Новые файлы лежат рядом с `network.go` в `_overlay/sing-box/route/` и
применяются тем же `prepare.sh`, что и REALITY. Кэш зависимостей не меняется.

**Как проверить.** Проверки выбора интерфейса запускаются в CI из исправленной
копии зависимости:

```bash
cd go/cmd/nekobox_core
MODFILE=$(bash _overlay/prepare.sh)
go test -modfile "$MODFILE" -tags "with_clash_api,with_gvisor,with_quic,with_wireguard,with_utls,with_v2ray_api" github.com/sagernet/sing-box/route -run TestPrivateDestinationInterface
```

На Windows отдельно проверяется собранное ядро с loopback mixed-прокси без
собственного TUN: внутренний HTTPS по IP и имени, DNS рабочего VPN по UDP
и TCP, публичный HTTPS через прежний прокси и обычный DNS. В тестовой
конфигурации нет статических привязок к TAP-адаптерам: путь выбирает правка.
Адреса организации и профили с ключами в репозиторий не включаются.

**Когда выбросить.** После перехода на версию sing-box, которая сама выбирает
маршрут Windows к частному адресу. Признак — те же проверки с рабочим VPN
проходят без копии `network.go` и помощников выбора интерфейса. Заплатка REALITY
при этом проверяется и удаляется отдельно.
