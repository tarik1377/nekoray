# Петля к собственному DNS TUN (#53)

## Подтверждённая причина всплеска TCP

Установленная 2.1.1 принимала TCP к виртуальному DNS `172.19.0.2:853`,
находила владельцем `greenrhythm_core.exe` и отправляла соединение через
`outbound/direct[bypass]` обратно на тот же адрес. В сохранённом участке
журнала это повторилось более 4300 раз с новыми портами и ID соединений.
Это устанавливает повторный вход исходящих соединений самого ядра в TUN.
Начальный запрос в сохранившийся участок не попал; его инициатор неизвестен.
Включённый в Windows DoT мог быть источником первого обращения, но это не доказано.

Ошибка выбора интерфейса: `NetworkManager.AutoDetectInterfaceFunc` вызывал
`interfaceFinder.ByAddr` до защищённого выбора частного маршрута.
`DefaultInterfaceFinder.ByAddr` ищет и точные адреса, и непосредственно
подключённые подсети. Для DNS TUN он возвращал сам TUN. Проверка имени и
описания proxy-интерфейса в `privateDestinationInterface` уже не выполнялась.
Каждый новый direct dial мог устанавливать ещё одно такое соединение.

Зафиксированные тысячи TIME_WAIT нельзя приписывать процессу по PID 0.
В данном случае принадлежность повторных соединений ядру установлена по
его журналу с ID, входным адресом, найденным процессом и исходящим адресом.
Уменьшение числа Established само по себе не доказывает отсутствия утечки.

## Исправление

1. Автовыбор исходящего интерфейса отказывает при выборе одного из собственных
   интерфейсов, зарегистрированных `InterfaceMonitor.MyInterfaces`, включая
   переименованный TUN. Это проверяется для on-link, рабочего VPN, частного и
   default-интерфейса. TAP, OpenVPN DCO, WSL и остальные интерфейсы сохраняются.
2. Только в Windows перед созданием ядра добавляются временные правила для
   DNS-адресов собственных TUN с `auto_route`. Адреса вычисляются так же, как
   в закреплённом sing-tun: следующий адрес первого префикса каждой семьи.
   Порт 53 передаётся DNS-службе; остальные TCP/UDP-сервисы этого виртуального
   адреса отклоняются до создания System TCP-сессии. `no_drop` не даёт серии
   повторов превратить отказ в молчаливое ожидание по обычному flood-лимиту.
3. Эти правила существуют только в памяти экземпляра. Файлы схем, подписки,
   пользовательские исключения, split DNS и маршруты Windows не мигрируются.
   Внешние DNS/DoT-серверы и адреса корпоративных ресурсов не входят в защиту.

Настоящий Windows CI выявил ещё два дефекта в закреплённом sing-tun:

* Правило Firewall отклонялось с `SCODE=0x80070057`, когда путь программы
  содержал короткие имена 8.3 (`RUNNER~1`). После раскрытия через
  `GetLongPathNameW` правило создаётся и TCP DNS отвечает. Ошибки настройки
  Firewall теперь попадают в журнал с исходным HRESULT/SCODE.
* Сформированные System-стеком TCP RST имели нулевой IPv4 TTL / IPv6 Hop Limit.
  Исправлены оба поля. Отдельный тест проверяет направления адресов и портов,
  SYN/ACK sequence, положительный TTL/Hop Limit и IP/TCP checksums. Без правки
  тест падает на нулевом TTL. Проверка по настоящему адаптеру также требует
  своевременного отказа, а не принимает таймаут за успех.

## Проверки

`TestTunDNSGuard*` запускает настоящий маршрутизатор и DNS с loopback-фикстурами.
Определение TUN удаляется до старта экземпляра. Проверяются TCP/UDP DNS, IPv4/IPv6,
1536 быстрых отказов без перехода в drop, контроль без защиты, произвольные адреса
адаптера и сохранность исходной конфигурации. Реальный адаптер на обычном ПК
при этих тестах не создаётся.

`TestAutoDetect*` в overlay использует настоящий `DefaultInterfaceFinder` с
таблицей фикстур. Проверяет собственную подсеть, IPv4-mapped IPv6, переименование,
ошибочный default и сохранность выбора других интерфейсов.

`TestWindowsRealTunDNSLoopGuard` разрешён только с отдельным флагом на одноразовом
Windows runner GitHub. Он создаёт System TUN с маршрутом исключительно к тестовому
`198.18.253.0/30`, проверяет TCP/UDP DNS, 64 реальных SYN/RST к виртуальному DoT и
отсутствие оставшихся Established/TIME_WAIT. CI запускает его на Windows Server
2022 и 2025. Успех этих заданий обязателен для публикации Windows-выпуска.

Для проверки счётчиков без запросов в сеть, перезапуска VPN и чтения подписок:

```powershell
Import-Module ./support/NetworkPressure.psm1
Get-GreenRhythmNetworkPressure | ConvertTo-Json -Depth 7
```

Отчёт включает состояния TCP, основные назначения TIME_WAIT, соединения к DNS
TUN, доступные события Tcpip 4227/4231/4266 за семь дней и режим дампа.
Недоступные данные перечисляются в Errors, а не выдаются за нулевые счётчики.
Модуль подключён и к обычному `support/collect-report.ps1`.

## Граница вывода о DPC watchdog

Дамп 24.10.2026 подтверждает `0x133`, single DPC timeout и ожидание spinlock
в `tcpip!TcpProcessExpiredTcbTimers+0x102 → nt!KeAcquireSpinLockAtDpcLevel →
nt!KxWaitForSpinLockAndAcquire`. Вызывающий обработчик:
`tcpip!TcpPeriodicTimeoutHandler+0xfc`. Это обработка истёкших таймеров TCP.
Подходящие публичные символы nt и tcpip загружены и проверены по образам
10.0.26100.8246. Дамп на серверы не передавался; CI использован только для
получения публичного PDB Microsoft, временное задание затем удалено.
Малый дамп не содержит читаемого контекста остальных процессоров и владельца
блокировки. Наличие Wintun/OpenVPN/фильтров виртуализации не устанавливает виновника.

Устранена доказанная петля и источник усиления нагрузки. Это не доказывает,
что именно она вызвала конкретный BSOD, и не является исправлением tcpip.sys
или стороннего kernel-драйвера. Часть #53 о владельце блокировки остаётся открытой
до получения соответствующих данных. Принудительный BSOD, Driver Verifier,
переключение драйверов, TCP-таймеров и режима дампа не выполнялись.

Ограничения малого дампа описаны в
[документации Microsoft](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/small-memory-dump).
