# Диагностика подключения и сервисов

## Реализовано в клиенте

В «Настройки → Диагностика соединения → Проверить» доступны общая проверка и Discord.
Запуск только по кнопке; текущие профили, маршруты, DNS, подключение и автопилот не меняются.

- 3 серии HTTPS-запросов либо 10 для более длительного наблюдения. Две независимые
  контрольные площадки; у Discord отдельно проверяется HTTPS API. Для каждого адреса
  сравниваются запрос без локального прокси и запрос через активный профиль с его правилами.
- Проверка подписки использует HTTPS GET с проверкой сертификата, пределом 1 МиБ и
  общим сроком ожидания. Ответ разбирает существующий импортёр в режиме `collect_only`.
  Полученные профили не сохраняются. HTTP 200 с HTML вместо подписки не считается успехом.
  Перенаправление показывается отдельно и автоматически не выполняется.
- Статус Discord запрашивается через официальный Statuspage API; он дополняет локальные
  результаты и не устанавливает причину отдельного сбоя.
- После обычных запросов отдельно проверяются текущий профиль без пользовательских
  правил и до двух различных альтернатив из только что полученного ответа подписки.
  Для каждого создаётся свой процесс установленного ядра с локальным смешанным входом
  и случайными реквизитами. Все назначения в нём явно направлены через проверяемый узел.
  В конфигурации нет TUN, правил пользователя, автопилота, статистики GUI или сторонних ядер.
  DNS для тестовых адресов идёт через проверяемый профиль; для имени самого узла используется
  системный bootstrap. Выбор сетевого интерфейса выполняет ядро без изменения маршрутов ОС.
- Для Discord и на рабочем пути, и в каждом отдельном ядре проверяются строгий TLS,
  WebSocket Upgrade, `Sec-WebSocket-Accept` и Gateway Hello (`op=10`). Вход в Discord
  не выполняется. Отдельно через SOCKS5 UDP ASSOCIATE отправляются по три DNS-запроса
  к двум независимым контрольным резолверам. Ответ должен совпасть по источнику,
  идентификатору и случайному имени вопроса; повторы и посторонние ответы отбрасываются.
- Альтернативы дедуплицируются по полному нативному outbound, включая реквизиты, но без
  названия профиля. Смена ключа при прежнем адресе остаётся новым кандидатом.
  Сохранённый профиль, удалённый из свежей подписки, не становится свежей альтернативой.
  Недоступная или нераспознанная подписка не заменяется старым кэшем.
- Подключение, версия ядра и режим фиксируются при запуске. Смена подключения отменяет
  проверку; старые результаты не выдаются за результат нового профиля.
- Отмена, повторы, время каждой пробы, HTTP-коды, классы ошибок, версия, ОС, стек/MTU,
  обезличенный идентификатор узла и отпечаток правил входят в JSON-отчёт.
  Ссылка подписки, её содержимое, UUID профиля, пароли, пользовательские имена профилей,
  адреса посещаемых страниц и IP клиента в него не входят. Отправки отчёта автоматически нет.

Каждый изолированный профиль получает три серии HTTPS-проб, максимум 18 секунд после
запуска ядра и 6 секунд на запуск. Вся проверка ограничена 140 секундами. Альтернативы
проверяются последовательно. Отмена, закрытие окна или смена подключения/правил/адреса
подписки прекращают пробы и завершают только созданный диагностикой процесс. Временная
конфигурация хранится в отдельном пользовательском каталоге с правами владельца и удаляется
после завершения процесса. Её содержимое, вывод ядра и секреты в журнал не передаются.

Цепочки, внешний front proxy, произвольный JSON и профили со сторонними ядрами/плагинами
помечаются неподдерживаемыми для изолированной проверки. Они не подменяются другим
транспортом. Свежий снимок обрабатывает не более 512 нативных кандидатов; при усечении
нельзя утверждать отсутствие текущего профиля. Сам импорт подписки не производится.

После проверки Discord доступно наблюдение за `Discord.exe`; его счётчики и интервал
добавляются в тот же отчёт при сохранении выбранного подключения. Учтённые ядром TCP/UDP-соединения
показывают выбранный маршрут, а не доставку пакетов. По ним не предлагается автоматически
вывести Discord напрямую. Успешный HTTPS не означает работоспособность голоса.

## Границы выводов

`system_no_proxy` не является независимой проверкой провайдера: TUN, корпоративный VPN
или другой перехватчик могут обработать и такой запрос. Поэтому в отчёте всегда
`independent_isp_baseline=false`. `profile_rules` также не является изолированным тестом
самого узла: пользовательское правило может выбрать прямой выход для контрольного адреса.

Доля неудачных HTTPS-запросов не является процентом потерь UDP-пакетов. Успех DNS по UDP
на контрольном адресе не подтверждает голосовую сессию Discord. Для неё нужны выбранный
голосовой сервер, WebSocket и UDP; сессионные токены Discord собирать нельзя.

Официальная документация:

- [Discord Voice](https://docs.discord.com/developers/topics/voice-connections)
- [Discord Gateway](https://docs.discord.com/developers/events/gateway)
- [Discord Status API](https://discordstatus.com/api)

Новые узлы автоматически становятся кандидатами после успешного чтения подписки.
Монитор или агент на каждом VPS не устанавливается, реестр адресов не ведётся.
Тестовая RPC-инстанция рабочего ядра не используется: сейчас она затрагивает общие
указатели статистики. Разделение процессами исключает это влияние.

### Необязательная независимая проверка

Внешние сети измерений существуют: например, [Globalping](https://globalping.io/) предоставляет
распределённые пробы ping, traceroute/MTR, DNS и HTTP
([официальная спецификация](https://github.com/jsdelivr/globalping/blob/master/public/v1/spec.yaml)).
Это дополнительная проверка сетевой доступности. Она не заменяет авторизованный запрос
через VLESS/Reality и проверку голоса в конкретной сессии.

Подключение внешнего измерителя — только отдельная необязательная функция, ещё не реализована:

- Цель получать из проверяемого профиля текущей подписки; статического списка VPS нет.
- Передавать только публичный адрес узла и необходимый порт. URL подписки, токены,
  UUID, ключи, корпоративные имена и внутренние IP внешнему измерителю не отправлять.
- Выбирать независимые сети и показывать реальные число/географию точек и время пробы.
  Если подходящих точек нет или API недоступен, локальная диагностика продолжает работать,
  а независимая проверка получает состояние «нет данных».
- Кратковременно кэшировать результаты по узлу и периоду, учитывать ограничения API.
  Одиночный таймаут не объявлять общей аварией.

При отсутствии подходящего независимого измерителя серверную часть не создавать.
Обобщение клиентских жалоб возможно только при добровольной отправке кратких отчётов;
отсутствие жалоб или отчётов не доказывает отсутствие ошибок. Фоновую телеметрию не включать.

| Наблюдение | Допустимый вывод / следующий шаг |
|---|---|
| Узел не проходит проверки из двух независимых сетей, контрольные адреса работают | Подтверждён общий отказ пути через узел; проверяем его вход, выход и профиль |
| Контрольные точки работают, у одного клиента ошибка | Единичный случай; сравниваем версию, правила, режим, тип ошибки и другую сеть |
| Текущий профиль не проходит, альтернативный из той же подписки проходит | Проблема текущего профиля или пути к нему; сам VPS и провайдер ещё не разделены |
| Изолированный профиль проходит, тот же профиль с пользовательскими правилами нет | Сравниваем маршруты, DNS и параметры ядра; последовательные пробы могли застать краткий сбой |
| HTTPS проходит, контроль UDP нет | Проблема UDP-пути; место отказа ещё не установлено |
| Контроль UDP проходит, голос Discord нет | Нужны данные голосового подключения, WebSocket/RTC и выбранного региона; общий UDP-тест не оправдывает ни сервер, ни провайдера |
| Один сервис не проходит на нескольких выходах, остальное работает | Возможен сбой сервиса или пути к нему; сверяем официальный статус и независимые сети |

Автоматические сбросы правил, отключение проверки сертификатов и переключение рабочих
VPN не являются диагностикой. Исправление должно соответствовать подтверждённой причине,
показывать ожидаемое действие и сохранять возможность отката.
